# rewrite-from-skill-bot

Telegram-бот, переписывающий сообщения в стиле из `runtime_skills/rewrite/SKILL.md`.
Стиль лежит в файле и подхватывается на лету — перезапуск не нужен.

## Поведение

Бот отвечает **только** если в сообщении есть упоминание `@username` бота.
Без упоминания он молчит: ни ответа, ни подсказки, ни обращения к LLM.

| Сообщение | Что переписывается | Пожелание |
|---|---|---|
| `@bot текст` | текст после упоминания | — |
| reply + `@bot` | текст или подпись reply-сообщения | — |
| reply + `@bot сделай короче` | текст или подпись reply-сообщения | `сделай короче` |
| reply + `@bot` (reply без текста) | — | ошибка: только текст или подпись к медиа |
| reply + `@bot` (в reply только `@bot`) | — | ошибка: в цитате есть только упоминание |
| `@bot` без текста и без reply | — | подсказка |
| reply без упоминания | бот молчит | — |
| обычное сообщение без упоминания | бот молчит | — |
| `@другойбот текст` | бот молчит | — |

При reply исходным текстом **всегда** является процитированное сообщение.
Текст рядом с упоминанием — только дополнительное пожелание и никогда не заменяет reply.
Упоминание внутри процитированного сообщения тоже вырезается из исходного текста.

Упоминание ищется по `MessageEntity`, а не подстрокой, регистр не важен.
Поддержаны `mention` и `text_mention`, а также `caption`/`caption_entities`.
Смещения считаются в UTF-16 code units, поэтому эмодзи перед упоминанием не ломают разбор.

## Как работает

1. `MentionFilter` пропускает сообщение только при реальном упоминании бота.
2. `AllowedChatFilter` отсекает чаты вне `ALLOWED_CHAT_IDS`.
3. `core/message_resolver.py` строит `source_text` и `user_instruction`.
4. Дедупликация по `(chat_id, message_id)`, затем rate limit.
5. `llm/client.py` собирает prompt из SKILL-файла и вызывает LLM.

Парсинг идёт **до** rate limit, поэтому пустые и некорректные запросы не расходуют квоту.

## Запуск

```bash
cp .env.example .env   # заполнить BOT_TOKEN, LLM_API_KEY, ALLOWED_CHAT_IDS
pip install -e ".[dev]"
python src/main.py
```

`ALLOWED_CHAT_IDS` обязателен: пустой список означает, что бот не отвечает нигде
(при старте пишется предупреждение в лог).

## Модель

По умолчанию — OpenRouter `poolside/laguna-s-2.1` (free):

```env
LLM_API_URL=https://openrouter.ai/api/v1/chat/completions
LLM_API_KEY=sk-or-...
LLM_MODEL=poolside/laguna-s-2.1
```

Любой OpenAI-совместимый endpoint работает через те же три переменные.

`response_format` не входит в список поддерживаемых полей этой модели и может дать 400,
поэтому `LLM_JSON_MODE=false` по умолчанию: клиент берёт `{"text": ...}`, если модель
вернула JSON, иначе использует текст как есть.

## Повторы и ошибки

| Код | Поведение |
|---|---|
| 429 | повтор с backoff, уважая заголовок `Retry-After` (потолок 30 с) |
| 5xx, timeout, connect error | повтор с backoff |
| 400, 401, 402, 403, 404 | без повторов, своё сообщение пользователю |

Всего 3 попытки. Паузы между попытками — экспоненциальный backoff с jitter:
`min(1.0 * 2^(n-1), 8 с)` плюс случайные 0–25 %. То есть примерно 1 с → 2 с → 4 с.
Константы `RETRY_BASE_SECONDS`, `RETRY_MAX_SECONDS`, `MAX_RETRY_AFTER_SECONDS`
заданы в `src/llm/client.py`.

Ответ 200 с некорректным телом (не-JSON, `choices` не список, `message` не объект)
повтором не считается — это ошибка модели, а не сбой транспорта.

Пустой ответ модели показывается как «пустой ответ», а не как внутренняя ошибка.
Тексты сообщений и ключи в логи не пишутся.

## Лимиты и защита от спама

Срабатывание лимита пользователя или чата отвечает один раз на ключ
(`(chat_id, user_id)` и `chat_id` соответственно). Пока не истечёт время,
указанное в ответе, бот молчит вместо повторных предупреждений.

Заглушка и rate limit живут в памяти процесса (`ponytail:` в
`core/rate_limiter.py`) — при нескольких инстансах нужен общий стор.
